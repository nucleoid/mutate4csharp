# Immutable input snapshots

Strict `check` capture treats the current Git worktree as input data. It resolves the requested base to one direct commit, retains the original requested revision for completion re-resolution, inventories cached and eligible untracked paths with Git, and copies the current working-tree bytes. This intentionally includes staged and unstaged changes; it does not substitute index or `HEAD` content for the bytes a developer asked to evaluate. A symbolic revision such as `HEAD` moving before completion is divergence even when the index and working-tree bytes are unchanged.

## Capture boundary

Capture is bounded independently by captured and ignored inventory counts, per-file bytes, total bytes, path depth, 32 MiB per Git stdout/stderr stream, and a 30-second timeout for each Git inventory command. Git streams are drained concurrently as raw bytes and decoded strictly only after the process exits, so malformed filename bytes cannot strand a writer behind a full pipe. Fully ignored directories are represented by directory names rather than every descendant. Git startup, limit, timeout, and decode failures are snapshot refusals and produce current-run evidence. Paths are length-framed into a SHA-256 capture identity together with the resolved base commit, exact Git index fingerprint, tracked/untracked state, deletion state, length, and content hash. File copies are streamed into a per-user, per-process private temporary hierarchy outside the repository (0700 on Unix); clone creation rehashes capture bytes against the recorded identity.

The following are excluded by name before content is opened: Git metadata, `.fire-off`, project-adjacent `bin`/`obj` build outputs, `TestResults`, `.mutate4csharp`, common IDE state, `.env` variants, certificate containers, user-secret files, and common credential directories. An ordinary source-controlled directory merely named `bin` or `obj` is not treated as build output unless its parent contains a captured project. Tracked excluded files that are not required are omitted without reading their content; the exact Git index fingerprint still binds tracked inventory metadata. Gitignored names are enumerated separately without opening their content: an ignored file beneath a captured project refuses capture unless it is covered by the secret, IDE-state, or project-output policy. Other common ignored trees such as `node_modules`, local appsettings, and received-test artifacts therefore refuse when they sit below a captured project unless a later policy explicitly proves them irrelevant.

Semicolon-separated static build paths are checked individually. Import lists refuse empty segments, and each nonempty segment independently receives imported-file normalization, extension, rooted-path, containment, exclusion, and captured-input validation. Every static, evaluation-time item `Include` is path-validated, including SDK-consumed item types outside the known path-item list. Dynamic `$(`, `@(`, and `%(` expressions are refused for known path-bearing items but remain allowed for non-path items such as `InternalsVisibleTo`; ordinary target-scoped generated/runtime items retain that behavior. Ordinary underscore-prefixed private items are not rejected by name. Instead, the explicit SDK 10.0.103 project-evaluation boundary also applies inside targets: it refuses unsafe dynamic `Include`/`Update` values and requires static values to identify captured `.csproj` files for the project-reference pipeline, the upstream `RestoreGraphProjectInputItems` source, and every item used directly by an SDK `MSBuild` task's `Projects` attribute. The pinned reserved self expressions `$(MSBuildProjectFile)`, `$(MSBuildProjectFullPath)`, and `$(MSBuildThisFileFullPath)` remain supported where a project-evaluation sink accepts a dynamic value. Static `Include` and `Update` values ending in any project extension other than `.csproj` are also refused independent of item name, while ordinary static C# `ProjectReference` items remain supported. Known path-bearing `Update` values are inspected using case-insensitive MSBuild names, including default `Compile`, `Content`, `None`, and `EmbeddedResource` items plus analyzer configs and generator inputs. `Remove` is subtractive and does not create an input dependency. A default/path-item `Update` glob refuses when it can affect omitted ignored, excluded, or secret inputs, while project `bin`/`obj` and `TestResults` output entries covered by SDK default exclusions do not cause refusal by themselves; custom non-path update globs do not invent input dependencies. Common path properties including `ApplicationManifest`, `Win32Resource`, and `RunSettingsFilePath` are inspected case-insensitively. Known restore-source, package-root/assets/output, intermediate-output, package-props, compiler/restore targets, MSBuild extension, and Directory Build/Packages/Solution import-redirection properties are refused rather than allowed to override the selected frozen configuration. This includes `RestoreGraphProjectInput`, `NuGetRestoreTargets`, `CSharpCoreTargetsPath`, `CSharpDesignTimeTargetsPath`, and NuGet's `_GenerateRestoreGraphProjectEntryInputProperties` forwarding bag observed in SDK 10.0.103.

As a name-independent backstop, each expression-free `PropertyGroup` value is resolved relative to its declaring build file and refused if it is rooted, drive-qualified, a file URI, rooted outside, or traverses outside the repository. Every semicolon part shaped as a static identifier `Name=Value` is first checked as a forwarding pair: redirector names refuse, while ordinary names have `Value` path-checked separately. The same pair and static-value checks apply to every non-control attribute and child metadata value on items outside targets, including item definitions; known path metadata such as `HintPath` must resolve to captured repository content. `ContainerWorkingDirectory` and `ContainerEnvironmentVariable` `Value` are logical paths inside a container rather than host filesystem inputs, and NuGet `PackagePath` is a logical path inside a package; these values retain encoded-octet and forwarding-pair checks but are exempt from host-path validation. Property-forwarding metadata named `AdditionalProperties`, `Properties`, `SetConfiguration`, `SetPlatform`, or `SetTargetFramework` on any evaluation-time item or item definition must contain no `$(`, `@(`, or `%(` expression and is then parsed as semicolon-separated static `Name=Value` pairs, so SDK item-list transformations cannot introduce an unvalidated restore or import redirector after parsing. The same forwarding check applies to known project-evaluation pipeline items declared inside targets. Static ordinary forwarding remains supported, including scalar, non-file URL, and repository-internal relative values. Repository-authored `MSBuild Projects` attributes in project files and imported `.props`/`.targets` accept only captured static `.csproj` paths or the pinned reserved self expressions. Their `Properties` and `AdditionalProperties` bags receive the same static forwarding validation; `RemoveProperties` must be a static list of ordinary property names and cannot name a known redirector. `AdditionalProjects` accepts only captured static `.csproj` paths. Task `Output` elements cannot populate these known project-evaluation item sinks, `AdditionalProjects`, or restore/import redirector properties. Dynamic output names are refused because they cannot be proven unrelated; ordinary static outputs remain supported. The SDK 10.0.103 project-reference pipeline items `ProjectReferenceWithConfiguration`, `_ProjectReferenceWithConfiguration`, `_MSBuildProjectReference`, `_MSBuildProjectReferenceExistent`, `AnnotatedProjects`, `UpdatedAnnotatedProjects`, and `ProjectsWithNearestPlatform` also receive the same dynamic-path refusal and C# project-extension checks as `ProjectReference`. The mechanically pinned direct SDK sink set is `_AllProjects`, `AssembliestoCrossgen`, `FilteredRestoreGraphProjectInputItems`, `FilteredRestoreGraphProjectInputItemsWithoutDuplicates`, `PackageReferencesToStore`, `StaticWebAssetProjectConfiguration`, `_CurrentRestoreProjectPathItems`, `_GenerateRestoreGraphProjectEntryInput`, `_InnerBuild`, `_InnerBuildProjects`, `_MSBuildProjectReferenceExistent`, `_ProjectConfigurationsWithEmbeddedPublishTargets`, `_ProjectConfigurationsWithPublishTargets`, `_ProjectReferencesFromAssetsFile`, `_ProjectsWithTFM`, `_ProjectsWithTFMNoBuild`, `_ProjectToTestWithTFM`, `_RestoreProjectPathItems`, `_RestoreProjectPathItemsWithoutDupes`, `_RidSpecificToolPackageProject`, `_StaticWebAssetProjectReference`, `_StaticWebAssetsEmbeddedProjectAssetConfigurations`, `_StaticWebAssetsProjectReference`, and `_WatchProjects`. A test rescans every SDK 10.0.103 `MSBuild Projects` attribute, classifies item-list, batching-identity, and reserved self-property forms, and fails on anything unclassified. Ordinary scalar, boolean, version, label, URL, and repository-internal metadata elsewhere remains valid. Refusal diagnostics identify context and unsafe property names without persisting raw forwarding, encoded, or dynamic build-input values. Any `%XX` MSBuild escape in any statically inspected property or item-metadata value, as well as in path-bearing imports, items, tasks, references, and globs, is deliberately refused before semantic parsing. This broad fail-closed boundary includes non-path values such as `%3B` in `NoWarn`; validation never reasons about text different from what MSBuild consumes. Import redirectors include every pure-property `Import Project="$(X)"` site in pinned SDK 10.0.103 plus the compound-import prefix `MSBuildSDKsPath`, and strict children clear those names case-insensitively before restore or test.

A preprocess or binlog is not used as the safety gate. Pre-evaluation generation would already load the imports under review. Adding a restore-time binlog after the static gate would not add execution, but it is defense in depth rather than closure of the build boundary: restore and build can import different files, deterministic import extraction would require a new binlog reader, and binlogs can retain environment/property values that this feature otherwise does not persist. The static encoded-octet rule plus the pinned-SDK import-property set close the concrete routes before restore without creating a new secret-bearing artifact. Dynamic custom properties that are not known path-bearing redirectors remain part of the documented trusted-build boundary.

Static `UsingTask AssemblyFile`, inline `Code Source`, and path-like RoslynCodeTaskFactory `Task/Reference Include` inputs must be captured inside the snapshot. Inline-task references containing dynamic expressions refuse before execution. Assembly-name-only references such as `System.Text.Json` remain valid.

Globs with no fixed prefix start at the declaring project folder, and a repository-root prefix covers the whole repository. They refuse when the fixed prefix intersects a collapsed ignored ancestor or a tracked excluded/secret path. Only an exact recursive folder exclusion (`dir/**` or `dir/**/*`) can prove the whole folder irrelevant; SDK 10.0.103 does not treat a trailing slash alone as recursive, narrower patterns are not widened, and Unix comparisons remain case-sensitive. Relative file-item paths in imported `.props`/`.targets` are refused because MSBuild resolves them per consuming project rather than per declaring file. The narrow supported imported-file form is a leading `$(MSBuildThisFileDirectory)` followed by a nonempty static suffix; capture resolves that suffix against the captured declaring file and applies the same escape, exclusion, and captured-input checks. Additional expressions, another leading property, and ordinary project-relative imported paths remain refused. Imports with extensions other than `.props`/`.targets` refuse because their contents are not parsed by this freezer. Project references and non-folder solution entries that are not C# `.csproj` files refuse rather than leaving another project kind's inputs uninspected; `.sln` solution folders are recognized by project-type GUID and skipped. A selected or statically referenced required input that falls in an exclusion is rejected, never silently omitted. `.snk` remains secret-bearing by policy: an unused tracked key is skipped without being opened, while `AssemblyOriginatorKeyFile` or explicit selection refuses capture rather than copying private key material. A missing or inaccessible explicit input produces a current-run `SNAPSHOT_REFUSED` report, replacing an eligible stale report at an explicit destination. Existing but uncaptured project `.user`, case-insensitive `NuGet.Config`, `Directory.Build.props`/`.targets`, `Directory.Packages.props`, `Directory.Build.rsp`, and `global.json` files on each project-to-root search path are refused by name without reading excluded secret content. A captured `Directory.Build.rsp` must be empty or whitespace-only; meaningful response-file content is refused until its full switch semantics can be frozen safely. The same fail-closed check covers `.editorconfig`/`.globalconfig` on captured source ancestor paths and `Directory.Solution.props`/`.targets` on captured solution ancestor paths. A `.globalconfig` above either the repository or private execution parent also refuses capture/execution because that search has no boundary directive. Symlinks, reparse points, special files, submodules, case-colliding paths, escaping project/import/resource references, rooted paths on inspected build-input surfaces, and dynamic MSBuild references that cannot be proven internal are rejected. Rooted paths are refused even when they point inside the repository because clone execution would preserve the literal and access the live original tree; project-file declarations can use equivalent captured relative paths, while imported declarations can use the narrow `$(MSBuildThisFileDirectory)` form. On Linux x64, each source is opened with `O_NOFOLLOW|O_NONBLOCK`, then `fstat` must confirm the opened handle is a regular file; this rejects FIFOs and sockets without a blocking open and closes the pathname check/open swap for the acquired handle. Missing native libraries or entry points fail closed into a current-run report. Linux arm64 and other Linux architectures are refused because their native `stat` ABI layout has not been validated here. Windows retains reparse/device checks; equivalent macOS special-file and check/open guarantees are not claimed. On Unix, a Git filename that is not valid UTF-8 is also refused because it cannot be represented safely by the current path model.

After copying, the tool re-runs Git inventory/index discovery and rehashes every original input. It repeats that validation immediately before report publication. Additions, deletions, index changes, link swaps, and same-size/same-timestamp content edits therefore make the run `INCOMPLETE` instead of lending a stale capture to a current-tree result.

This is observed validation, not a transactional filesystem primitive. A same-bytes ABA change between observations is not distinguishable, and a change can occur after the final check. Reports state this boundary instead of claiming an atomic OS snapshot.

## Execution workspaces and dependencies

Baseline and every mutant receive a fresh clone made only from captured bytes. Baseline `bin`, `obj`, test results, generated files, and side effects are never copied into a mutant. Text mutations preserve the captured encoding preamble and untouched newline/trivia bytes; only the selected text span changes. Coverage paths emitted from a clone can be mapped back to canonical original-root paths.

Dependency preparation runs `dotnet restore -m:1` only inside a private preparation clone with a private package root and exactly one captured applicable `NuGet.Config` on every requested project/solution ancestor chain. A hierarchy that NuGet would merge is refused rather than replaced by the nearest file; unrelated nested configs are ignored, and entries resolving to different single configs are refused. The selected config must explicitly `<clear/>` inherited `packageSources`; any `packageSourceMapping` in that same config is preserved. NuGet and MSBuild fallback-package-folder settings are refused, restore overrides both fallback properties to empty, removes `NUGET_FALLBACK_PACKAGES` from child environments, and requires every generated `project.assets.json` to name only the private package root. Each assets graph's recorded restore sources must be a subset of the sources declared by that explicitly selected config, with one pinned-SDK exception: SDK 10.0.103's `Microsoft.NET.NuGetOfflineCache.targets` may add exactly `$(NetCoreRoot)library-packs` when that directory exists. This is a machine-install source rather than a source declared by the selected config; `packageSourceMapping` can exclude it from package resolution. Any restored package content obtained from it is copied into the private package root and fingerprinted with the rest of the resolved package content. Package-bearing and `PackageDownload` graphs that omit source provenance are refused. Pinned SDK 10.0.103 treats the string `clear` in those MSBuild properties as a literal folder, so XML `<clear/>` semantics must not be assumed for command-line properties. Apart from that exact SDK-added machine-install source, the tool never authorizes nuget.org or another package source that is absent from the selected config: absent or ambiguous repository configuration is refused so user/machine source policy cannot silently become a public-feed lookup. Existing `packages.lock.json` files use locked mode; otherwise a private lock is generated in the clone, never the original. The deterministic locks, package bytes, capture identity, and SDK version are fingerprinted. Each evaluation attempt currently receives a separate writable package-cache copy plus the prepared lock, performs a locked restore, and runs tests with `--no-restore`; package content is re-fingerprinted before cleanup. Disk and hashing cost therefore scales with evaluated mutants, not only configured worker concurrency. No lockfile is required or created in the original tree, no original `bin`/`obj` is written, and credentials are not copied into the frozen package store or report. Preparation clone creation is bounded by the same overall dependency deadline. Failure to produce or enforce a bounded resolved graph is inconclusive, never success.

## Supported and unsupported inputs

The snapshot freezes repository files and materialized package content. Strict restore/test children remove inherited restore/import-redirection property names case-insensitively, using the same rule as capture; this includes public Directory Build/Packages properties, `CustomBefore*`/`CustomAfter*`, intermediate/assets/output/source properties, compiler/restore target paths, SDK-private names, and `MSBuildSDKsPath`. They also clear `DOTNET_MSBUILD_SDK_RESOLVER_SDKS_DIR`, `DOTNET_MSBUILD_SDK_RESOLVER_SDKS_VER`, `DOTNET_MSBUILD_SDK_RESOLVER_CLI_DIR`, and `MSBUILDADDITIONALSDKRESOLVERSFOLDER`. Restore and test both pin `NuGetPackageRoot` to the private package cache. Legacy execution does not receive these strict-only overrides. It does **not** otherwise freeze databases, HTTP services, clocks, randomness, unrelated environment variables, machine-wide SDK/workload changes after preparation, files opened dynamically by tests, `.git`-dependent build logic, arbitrary custom-task side effects, or other processes able to mutate external state. Test and build code remains trusted code, not a security sandbox. Such dependencies must be removed, explicitly modeled by later configuration/orchestration work, or reported as unsupported/incomplete.

Owned temporary directories are created beneath the requested per-user/category parent, carry an unguessable ownership marker, and cleanup validates both parent containment and that marker. The process-private root has a separate marker and active-owner count. Active-owner accounting is released even when marker validation or deletion fails; the original capture/cancellation failure and cleanup failure are both retained in cleanup evidence. After the last owned child is disposed, cleanup removes only empty category directories and a root containing only its matching marker; active or foreign paths are preserved. Every clone's private parent contains exact terminating `Directory.Build.props`, `Directory.Build.targets`, `Directory.Packages.props`, `Directory.Build.rsp`, `Directory.Solution.props`, `Directory.Solution.targets`, `.editorconfig`, and SDK-pinning `global.json` files. Those boundaries are revalidated immediately before restore/test; NuGet configuration is explicit, only an empty or whitespace-only captured repository `Directory.Build.rsp` is accepted, and reusable MSBuild/compiler servers are disabled. The empty response file at the marker-validated private parent terminates inherited lookup above the clone. Strict restore and test processes override `MSBuildUserExtensionsPath` to a private owned path and remove inherited `MSBuildExtensionsPath` environment overrides, preventing machine/user `ImportBefore` and `ImportAfter` content from becoming uncaptured inputs while retaining the SDK's default extensions path. Configuration above that private boundary is not treated as reachable input except `.globalconfig`, whose search has no terminating directive and therefore refuses execution when present above the private parent. If marker-validated cleanup fails, the failure is recorded before report publication instead of contradicting an already-published result. Test results stay inside the same owned private root. Unrelated temporary paths are never cleanup targets.

These MSBuild limits were measured on Linux with the pinned SDK 10.0.103: an outer `Directory.Packages.props` affected project builds; an outer `Directory.Build.rsp` affected restore, build, and test; and outer `Directory.Solution.props`/`.targets` executed for a `.slnx` build. The corresponding private-parent files terminated each observed search while a repository response file inside the clone remained applicable; `-noAutoResponse` suppressed both and therefore caused input drift. The same SDK included direct and nested files beneath `Exclude="dir/"`. Equivalent Windows and macOS search, ACL, and reparse-point behavior is not claimed by that experiment and remains platform-specific validation work.

Strict mode handles Ctrl+C and, on Unix, SIGTERM by cancelling the same token used by Git, capture, dependency preparation, and workers. A second termination signal is not swallowed and may force the platform's default termination. Cancellation and timeout call the runtime's process-tree kill API, await launched processes, and dispose marker-validated owned directories before publishing an incomplete cancellation report when possible. Restore, SDK probing, and `dotnet test` share this path; each stdout/stderr stream is capped at 32 MiB and pipe draining after exit/kill is capped at five seconds. A drain or descendant-cleanup failure retains the primary timeout/cancellation as cleanup evidence. Strict snapshot tests retain repository response-file semantics while disabling node/compiler reuse; legacy tests retain their prior arguments while sharing bounded output and process cleanup. On Linux, cleanup records observable descendant PIDs and kernel start times before the kill, then waits for those exact identities to disappear from `/proc` or enter zombie state; a zombie has terminated and cannot retain the owned workspace even when the host's process 1 delays reaping it. Start-time matching prevents PID reuse from being mistaken for the original process. Termination must complete within five seconds or cleanup fails explicitly instead of returning while a live recorded identity remains. This covers ordinary cooperative interruption and the child/grandchild tree in the Linux regression fixture, but `/proc` discovery is observational rather than an atomic fork barrier and other platforms only provide the runtime process-tree guarantee. It is not a containment primitive: SIGKILL, power loss, runtime termination, a descendant created during discovery, or one that deliberately detaches with `setsid`, double-forking, or an OS-specific equivalent can escape cleanup and leave the process-private tree behind. Automatic stale-directory sweeping is deliberately deferred because portable PID/liveness checks cannot safely distinguish all active or foreign directories; stale paths may be removed only after validating the ownership marker and confirming no run is active. No sandbox guarantee is made.

## Current strict gate

The strict pipeline publishes a validated snapshot identity, versioned suite mapping, frozen dependency identity, fresh baseline/coverage, and isolated mutation evidence. Supported Git-backed configuration-v1 contexts produce canonical mutation and evaluation-unit identities from captured bytes and report real executed outcomes. Until final verification is connected, those reports remain `INCOMPLETE` with `FINALIZATION_PENDING`; refused or unsupported contexts retain an unknown enumeration count and their exact refusal reason. Partial evidence cannot manufacture `PASS`.
